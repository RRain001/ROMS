# Independent single-grid build/run template for UD1K and L3

These are parameterized copies of the ES3K case configuration. They are **templates**, not active child cases. Replace every `${CASE_CPP}` / `${CASE_SLUG}` and source/grid/forcing placeholder before placing them in `ROMS_Nesting/Data_pre/cases/<name>/config`. They never enable ROMS native `NESTING` or contact.nc. Each level has its own executable, grid, forcing, run directory and logs.

1. Keep the existing `build_context.py`, `run_context.py` and public entry points. Copy the configuration templates, choose a distinct case name, CPP name and executable, and set `paths.case_root` beneath `ROMS_Nesting/projects`. Set `paths.active_grid` to a case-specific canonical filename.
2. Supply that case's own `project_parameters.json`: accepted geometry, sigma coordinates, physical parameters and MPI tiles. N=41 is ES3K's present setting, not an automatic scientific approval for another grid. `NtileI*NtileJ` must match configured `np`.
3. Set `external_test_config.json` to that grid's verified source SHA256, dimensions and wet count, recorded archive URL, test dates and paths. The current registrar expects the archived ES3K provenance/strait contract; do not invoke that ES3K scientific audit on UD1K/L3. Reuse the checksum-copy mechanism but supply each child grid's existing audit/manifest contract.
4. Copy/adapt `Data_pre/cases/JAPAN_SEA/templates/japan_sea.h` to `<case_slug>.h` only after verifying child physics. Retain external initial/boundary fields, external ERA5 bulk forcing and configured SSH/UV tides; source release remains disabled until scientifically specified. Do not use ANA_GRID/ANA_INITIAL or native online contact nesting to fill absent data.
5. Select the platform explicitly. Default Linux Intel profile matches the user's FDNPP baseline. GNU/OpenMPI Linux and macOS/Homebrew profiles are separate, available via `--config`; they are not validated by the Intel build. Set matching run configuration with `--config` too. Never combine a GNU MPI wrapper with Intel NetCDF modules.
6. Use the existing `.in` generator (`Data_pre/scripts/run_support/create_pilot_infile.py`) with `--forcing-mode external`, `--start-time`, `--stop-time`, explicit input paths and one `external_startup/external_1h/external_6h/external_24h` mode. These modes do not change the formal case dates and refuse to shorten a test to fit insufficient boundary coverage.
7. Parent history supplies each child's offline one-way boundary files through the existing nesting preprocessor. ES3K uses GLORYS on its outer boundary; child configurations must reference their own parent-derived initial/boundary products. Do not feed the ES3K GLORYS sample or its files to a child by default.
8. Run toolchain ABI validation, the existing case build command, NetCDF checks and runtime prerequisites before launch. A template, successful compile or static grid audit is not numerical acceptance. Test progression remains manual and stops on the first failed physics/stability gate.

A future child case must also update the isolation check's approved case inventory intentionally; no UD1K or L3 case has been activated here. Production dates and UD1K Option B approval remain unresolved.
